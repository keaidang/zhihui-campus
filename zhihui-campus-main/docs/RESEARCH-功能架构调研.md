# 一站式校园系统 · 功能架构调研与方案（已确认 ✅）

> 2026-09-17 · 调研目的：在写代码前对齐"角色体系 + 功能模块"总架构
> 结论先行：采用市面通行的 **五层架构 + RBAC 五角色**，与现有 EdgeOne 全栈地基完全兼容
>
> **✅ 2026-09-17 用户已确认三项决策：**
> 1. 角色体系 = **五角色**（student / teacher / counselor / leader / admin）
> 2. 一期（M1）= **教务线 + 学工线并行**（选课+成绩 与 请销假审批流同步开工）
> 3. **砍掉"校园点餐"**模块（涉及支付链路，毕设不做半成品）

## 一、调研来源（市面通行做法）

| 来源 | 关键结论 |
|---|---|
| 超星"学习通"学工平台（某高校智慧社区总结） | 九大模块：基础设置/迎新/学工/第二课堂/宿舍/日常/离校/应用/终端；核心是"学生在校全周期" |
| 高校智慧学生服务平台建设方案（全国高校思政网收录） | 通行骨架 = 统一身份认证 + 服务大厅（业务中心/任务办理/服务评价）+ 用户统一管理（分级授权）+ 统一消息 + 流程引擎/表单引擎 + 基础主数据（学院/专业/年级/班级/宿舍） |
| 一站式办事服务运营平台方案（厂商方案） | 三层：统一门户（单点登录/统一消息）→ 一站式办事平台（教职工办事中心 + 学生办事中心）→ 后端 MIS（教务/学工/财务/资产）；大数据层做学生画像 + 风险预警（学业/失联/消费异常） |
| 智慧学工管理系统手册（网硕互联） | 角色拆法：系统管理员 / 学工处老师 / 辅导员班主任 / 学生；学生信息、学籍异动、奖惩助贷、请销假、综合测评是学工系统标配 |
| 学生管理系统实战文章（哲迈云/CSDN） | RBAC 模型 + 审计日志是一切的地基；MVP 收敛策略："学生主线功能做到能用，管理端做到可演示" |

**共识总结**：不管厂商怎么包装，所有系统都是五层——

1. **入口层**：统一门户（PC + 移动）· 统一身份认证 · 统一消息
2. **服务大厅层**：服务分类 · 在线申请 · 进度跟踪 · 服务评价
3. **业务应用层**：教务（选课/成绩/课表）· 学工（请假/奖惩/宿舍/迎新离校）· 生活服务（图书/报修/消费）· 校园社区（二手/失物/社团）
4. **数据决策层**：学生画像 · 统计报表 · 风险预警 · 领导驾驶舱
5. **支撑底座**：RBAC 用户权限 · 流程审批引擎 · 数据字典 · 操作审计

## 二、角色体系方案（RBAC 五角色）

现有 `sys_role` 表天然支持多角色，只需加种子数据。市面通行拆法 + 毕设规模收敛：

| 角色 | code | 定位 | 核心功能 |
|---|---|---|---|
| 学生 | `student` | 服务消费者（用量最大） | 选课、查成绩课表、请假申请、报修、社团活动、二手/失物、公告浏览 |
| 教师 | `teacher` | 教学执行者 | 开课/课表、成绩录入、公告发布、教师版驾驶舱（任教班级） |
| 辅导员/院系管理员 | `counselor` | 学生管理者 | 本院学生信息、请假审批、奖助初审、报修派单、本院报表 |
| 校领导 | `leader` | 只读决策者 | 全校数据驾驶舱、统计报表、风险预警（无任何写操作） |
| 超级管理员 | `admin` | 系统运维 | 用户/角色/权限、数据字典、公告置顶撤回、操作日志 |

- JWT 载荷已带 `roles` 数组，一个人可以多角色（如教师兼辅导员）→ **零架构改动**
- 毕设规模建议：权限点直接用"角色 + 数据范围（本人/本院/全校）"代码级判断，暂不建 permission 表（论文里说明可扩展即可）

## 三、功能模块规划（四期）

| 期 | 模块 | 内容 | 亮点 |
|---|---|---|---|
| 地基 ✅ | 统一认证 | 注册/登录/双令牌/RBAC 骨架 | 已上线 |
| M1 | 教务线 | **选课**（开放名额、并发扣位、退改选）+ 成绩录入/查询 + 课表 | 并发控制 = 论文核心亮点 |
| M2 | 学工线 | **请销假审批流**（学生申请→辅导员审批→销假闭环）+ 公告通知 + 宿舍报修工单 | 流程引擎雏形 = 第二亮点 |
| M3 | 生活服务线 | 图书借阅、二手集市、失物招领、社团活动、运动打卡（轻业务，快速铺量） | 覆盖原 PRD 8 卡片 |
| M4 | 数据决策线 | 校领导驾驶舱（全校统计看板）+ 教师/辅导员分级报表 + 简版学生画像 | 呼应"云边协同数据分析" |

对应原 PRD 8 卡片映射：课程选课→M1；图书借阅/校园点餐→M3；宿舍生活→M2；二手集市/失物招领/社团活动/运动打卡→M3；新增：成绩课表(M1)、请销假/奖助(M2)、驾驶舱(M4)。

## 四、关键技术设计预判（写进论文的点）

1. **选课并发**：TiDB 事务 + 名额条件 UPDATE（`UPDATE ... SET used=used+1 WHERE id=? AND used<capacity`）+ 唯一键防重复选课
2. **审批流**：通用 `flow_instance/flow_node` 两表驱动，请假/奖助/报修共用一套流转逻辑（毕设规模的"流程引擎"）
3. **数据范围控制**：`本人/本院/全校` 三级 scope，SQL 层强制拼接 WHERE，前端只做展示过滤
4. **驾驶舱**：聚合 SQL + EdgeOne 边缘缓存（KV 缓存报表结果 60s），呼应云边协同
