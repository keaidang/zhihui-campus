# 论文重点梳理

> 依据：本项目（zhihui-campus）实际实现 + docs/ARCHITECTURE.md 决策记录 + docs/AUDIT-2026-09-21.md 体检结论
> 开题题目：《基于云边协同与 Serverless 架构的"智汇校园"一站式服务平台设计与实现》
> 本文档回答三个问题：**论文该重点写什么 / 每个重点的证据在哪 / 答辩会被追问什么**

---

## 一、一句话定位

**用"云边协同 + Serverless"这套新架构范式，把校园里原本分散的一堆信息化系统（选课、学工、宿舍、图书、论坛…）收敛成一个统一平台**——而论文的价值不在于"做了多少功能"，在于**在真实平台上验证了这套架构的边界、踩到的坑、以及为绕开坑所做的机制设计**。

> 写作时的核心立场：**工程结论 > 功能罗列**。功能清单放第 4 章表里即可，"为什么这么设计、实测发现什么不对、于是改成了什么"才是论文的肉。

---

## 二、三大核心贡献（论文主体，占 70% 篇幅）

### 贡献 1 · 云边协同架构的落地与边界验证 ★★★（对应标题，最重要）

**做了什么**：基于腾讯云 EdgeOne Pages 的**双运行时**构建三层架构——

| 层 | 载体 | 承担 | 不承担 |
|---|---|---|---|
| 边缘 | Edge Functions（V8 沙箱 + KV） | 静态资源全球分发、边缘原生轻端点（KV 访问统计）、边缘缓存 | 数据库访问（无 TCP）、重业务 |
| 云端 | Node Functions | 业务 API、事务、鉴权、入口限流 | 静态分发 |
| 数据 | TiDB Serverless | 结构化数据 + 强一致事务 | 高延迟容忍的计数（用 KV） |

**最有价值的部分是"发现平台边界"的过程**（这段是论文与普通毕设的分水岭）：

- 原设想做一个**边缘限流网关**（边缘侧 KV 限流 + 黑白名单 + 跨域回源代理）→ **实测发现 EdgeOne 边缘函数的同域 fetch 子请求不进函数路由**（落到静态层返回 SPA），代理架构在该平台**不可行**，于是回滚；
- 回滚后限流改到 Node 侧，又连踩两坑：① **多实例内存不共享**（内存限流 30 连发零触发）② **`x-forwarded-for` 是边缘出口代理池 IP**（按 IP 计数被稀释）→ 最终改为**基于数据库流水计数**（登录用 `sys_login_log` 失败流水、发码用 `sys_email_code`）；
- 结论沉淀为可复用的架构判断：**边缘只放"无状态、无 DB 依赖、容忍最终一致"的能力**，需要强一致与事务的一律落云端。

**证据**：`docs/ARCHITECTURE.md` 第 1 节（含答辩口径）、2.5 节双运行时分工表、ADR-8；变更记录里"边缘网关试错与回滚"全程留痕（3 个回滚 commit + 3 个方案 B commit）。

**建议论文呈现**：一张三层架构图 + 一张"边缘能力可行性判定表"（哪些能力实测可行 / 不可行 + 原因）。

### 贡献 2 · 高并发选课的名额一致性控制 ★★★

**问题**：选课是典型的"热点写"场景——同一门课短时间内被大量学生抢，必须**不超卖**（容量 60 就不能选出第 61 个），同时不能因为锁把系统拖死。

**方案（三层防线，层层兜底）**：

1. **唯一键占位**：`edu_elect` 的 `(student_id, class_id)` 唯一键，从数据库层面杜绝重复占位；
2. **条件 UPDATE 扣名额**：`UPDATE edu_class SET taken = taken + 1 WHERE id = ? AND taken < capacity` —— 用**返回的受影响行数**判断是否抢到，而非先查后写；
3. **事务包裹 + 瞬时错误重试**：整个选课动作在一个事务内完成，配合 Serverless 数据库的瞬时错误自动重试。

**为什么这比"标准答案"更值得写**：论文里通常会写 `SELECT ... FOR UPDATE`（悲观锁）或版本号乐观锁，本文可以**对比三种方案**并说明选择理由——
- 悲观锁：热点行锁竞争激烈，Serverless 环境下连接持有时间长，易触发连接超时；
- 乐观锁：需要重试循环，热点场景退化严重；
- **条件 UPDATE**：把"判断 + 修改"合并为一条原子语句，无显式锁、无重试循环，天然幂等。

**证据**：`node-functions/api/edu/*`、`docs/ARCHITECTURE.md` 技术亮点 1、线上 15/15 并发压测零 500、seed 后超员核实为 0。

**建议论文呈现**：三种并发控制方案的对比表 + 条件 UPDATE 的原子性论证 + 压测数据。

### 贡献 3 · 业务零侵入的通用审批流引擎 ★★

**方案**：两表驱动，与具体业务解耦——
- `flow_instance`：谁发起的什么业务、走到哪、状态如何；
- `flow_node`：每个节点一个**处理角色**（非指定人）+ 处理留痕（谁、何时、结论、意见）。

**关键设计点**（都是可讲的深水区）：
1. **业务零侵入**：新增审批类业务只需"建业务单据表 + 插 instance + 按 `node_order` 插节点"，**不新增任何流程代码**；
2. **处理人实时匹配**：`handler_role` + 数据范围联合匹配（辅导员只审本院学生）——避免把处理人写死，也避免越权；
3. **节点留痕可追溯**：每次审批写 node，形成完整流转链。

**⚠ 必须主动说明的设计边界**（审计发现的 P1-2）：**报修不走审批流**——报修是"单节点受理工单"（提交→受理→完成的状态机），不是多节点审批。论文里应明确写"通用审批流适用于请销假、社团申请这类**需多节点审批**的业务；报修属于**非审批型工单**，采用状态机"。主动划清边界比含糊其辞更能体现设计思考。

**证据**：`schema-004-affair.sql`、`docs/ARCHITECTURE.md` ADR-7、线上 16 步验证中的审批→销假闭环。

## 三、次级支撑点（占 20% 篇幅，挑 2~3 个写）

| 点 | 讲什么 | 证据 |
|---|---|---|
| **RBAC + 数据范围双维权限** | guard.js 三层防线：路由守卫 → 实时查库 → SQL 强制拼接；五角色（学生/教师/辅导员/校领导/超管） | 越权回归测试返回 40301；ADR-5 |
| **Serverless 数据库韧性** | TiDB Serverless 的瞬时错误识别（`PROTOCOL_CONNECTION_LOST`）→ 退避重试 + 连接池；错误落库 `sys_op_log` 支撑远程诊断（边缘运行时无日志控制台） | ADR-6；压测零 500 |
| **存储选型论证** | KV / Blob / 关系库三者分工：**KV 是 60 秒最终一致 → 绝不能承载选课扣名额**；DB 存元数据 + LONGBLOB 暂存图片（预留切图床的接缝） | ADR-2、ADR-4 |
| **全站时间口径统一** | TiDB 会话时区为 UTC、mysql2 连接时区配置错误会导致**全站时间偏 8 小时**（连带刷新令牌多活 8h、60s 频控失效）——一个"看似小问题、实为系统性缺陷"的排障案例 | 铁律 #25 |
| **前端工程化** | EP 按需引入使最大 chunk 从 1088KB 降到 172KB；移动端适配（22 路由零横向溢出、PC 端零改动） | 铁律 #27~#33 |

## 六、答辩追问口径（提前准备，避免临场卡壳）

| 可能被问 | 建议回答框架 |
|---|---|
| **"边缘计算在你的项目里体现在哪？"** | 已有标准口径：静态资源就近分发（毫秒级）、图片边缘缓存不回源、**边缘原生轻端点（KV 统计/诊断）毫秒级响应**；核心业务与强一致事务在云端——"三层各司其职"。**并主动补一句实测边界**：同域子请求不进函数路由，所以没做边缘代理网关（这句会显著加分） |
| **"为什么不用微服务/SpringCloud？"** | 单人毕设，注册中心/网关/链路追踪的运维负担换不来收益；且 Serverless 本身已解决弹性与运维问题（ADR-1） |
| **"并发选课怎么保证不超卖？"** | 见贡献 2，重点讲**条件 UPDATE 的原子性**，并给出与悲观锁/乐观锁的对比 |
| **"为什么不用 KV 存全部数据？"** | KV 60 秒最终一致 → 选课会超卖；KV 无条件查询/JOIN/事务（ADR-2） |
| **"为什么没做小程序？"** | 主动说明：个人主体无法使用 web-view；纯套壳易被拒审；小程序自身亦须 ICP 备案 → **改用"响应式 H5 + App 壳"替代**（这是**有依据的技术决策**，不是"没做完"） |
| **"有没有做单元测试？"** | 如实回答：以**脚本化线上冒烟（16/21 步）+ 数据一致性体检（18 类）+ 安全审计**为主，**未建立单元测试体系**，这是本项目主要工程短板，已列入展望 |
| **"系统真跑起来了吗？"** | 给出线上地址 `https://c.9o.pw`，并说明演示账号；强调是**Git push 自动构建部署的真实生产环境** |

## 七、写作注意事项（诚实口径 = 加分项）

### 7.1 必须主动说明的"不做清单"（防止被当成缺陷）
- 校园点餐（涉及支付链路，做"预订不支付"易显半成品）
- 真实支付、真实短信/公众号推送（站内信替代）
- 微信小程序（见上）

> 主动说明边界，比被问倒要好得多——这体现的是**需求裁剪能力**。

### 7.2 "不足与展望"应如实写三条（显得专业）
1. **缺少自动化测试体系**：目前依赖脚本化冒烟与人工回归，未覆盖单元测试（这是最大的工程债）；
2. **图片仍存于业务库**（LONGBLOB 暂存），未接入对象存储——但已预留切换接缝（只改 blob 服务与上传组件的 URL 生成）；
3. **未做多租户/多校区**扩展设计。

### 7.3 三个"能体现工程严谨性"的细节（建议写进正文）
1. **限流方案的两次修正**（内存版失效 → 出口 IP 被稀释 → DB 流水计数）：说明"结论是靠实测拿到的"；
2. **时间口径的全站统一**：从"驾驶舱时间显示错乱"这个表象，追到"连接池时区配置错误导致全站偏 8 小时、连刷新令牌都多活 8 小时"的系统性缺陷；
3. **表格被压扁的回归**：为消除横向溢出而给表格加 `max-width`，反而让 11 列压成 42px 不可读——**"消除溢出不能以牺牲可读性为代价"**，并由此建立了"溢出 + 列宽"双断言验收口径。

> 这三点共同说明一件事：**项目是按工程标准在迭代（发现问题 → 定位根因 → 修复 → 建立防回归机制），而不是一次性写完就交**。这是毕设论文最容易出彩、也最容易被忽略的部分。

## 八、一句话总结

**论文的骨架是"云边协同架构"（贡献 1，回答"用什么架构"），血肉是"选课并发控制"与"审批流引擎"两个机制级设计（贡献 2、3，回答"难在哪、怎么解决"），可信度来自线上真实环境 + 可复现的验证数据（第四、五节）。而真正能拉开差距的，是把踩坑、修正、建立防回归机制的过程如实写出来。**
