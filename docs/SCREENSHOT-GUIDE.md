## 二、论文里有两处表述与实现不符，建议改

### ① 4.2 节「满员时按钮自动置灰」——实现不是这样

原文：

> 选课页界面见图 4-3所示：左侧按课程代码与时间排列教学班，右侧以进度条显示余量，**满员时按钮自动置灰**，学生无需提交后才获知名额已满。

实际实现（`src/views/edu/ElectView.vue`）：**显示余量，但按钮不禁用**；
提交后由服务端条件更新判定，返回 `42005` 与可读提示。

**建议改为：**

> ……右侧以进度条显示余量；提交时由服务端条件更新判定，若名额已满返回 42005 并提示「课程名（星期节次）名额已满（已选/容量），可关注退课释放的名额」。**故意不在前端禁用按钮**：前端置灰只是观感，真正的防超卖必须由数据库的条件更新保证（见 4.2 第二层），前端拦截反而会掩盖并发下的真实行为。

这样改的好处：**把"没做前端拦截"变成论据**——正好呼应你 4.2 的核心论点"正确性不依赖应用层的检查"。

### ② 4.4 节的「系主任」——系统里没有这个角色

原文与口头描述里说"申请人 → 辅导员 → 系主任"，但角色表只有
`admin / student / teacher / counselor / leader` 五种，没有"系主任"。

实际实现（本次补齐）：**辅导员审批 → 院系复核**，第二级用 `leader` 角色承载。

**建议统一表述为「院系复核」**，或加一句说明：

> 第二级复核环节在实现中由 `leader`（院系/校级管理角色）承载；系统未单独定义"系主任"角色，
> 因为论文 4.4 强调的是「处理人按角色 + 数据范围实时匹配」而非固定岗位——
> 新增一级只需在节点定义中追加一行，无需改动表结构与流程代码。
