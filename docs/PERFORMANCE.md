## 2. 数据库延迟实测（TiDB Cloud Serverless，v8.5.3-serverless）

### 2.1 每次新建连接（最坏情况：Serverless 冷路径）

| 样本 | P50 | P90 | 最大 | 失败 |
|---|---|---|---|---|
| 连续 40 次「建连 + `SELECT 1` + 关闭」 | **2682 ms** | 4053 ms | 5509 ms | **0 / 40** |

首次建连（含 TLS 握手）实测 **2090 ms**。

> 这就是"Serverless 冷启动"的真实代价：**每次新建连接要 2 秒左右**。
> 但它只在"连接池里没有可用连接"时才发生 —— 也就是函数实例刚冷启动的第一批请求。

### 2.2 连接池复用（线上实际运行方式）

线上 `lib/db.js` 用 `mysql.createPool({ connectionLimit: 5, enableKeepAlive: true })`。

| 样本 | P50 | P90 | P99 | 最大 | 失败 |
|---|---|---|---|---|---|
| 连续 100 次池化查询 | **471 ms** | 1201 ms | 4124 ms | 4124 ms | **0 / 100** |

### 2.3 池化连接空闲后复用（模拟 Serverless 冷间隙）

空闲 **70 秒** 后再连续查 3 次：`297ms / 276ms / 226ms`，**0 失败**。

服务端 `wait_timeout = 28800`（8 小时），`system_time_zone = UTC`。
→ **闲置连接不会被服务端随手杀掉**，本项目的"从库查到活动间隔"远小于 8 小时，不构成风险。

### 2.4 结论

- **可用性：140 次连续测试 0 失败**。说"数据库错误率高"没有数据支撑。
- **延迟：池化后 P50 0.5 秒、P90 1.2 秒**。对校园系统的交互场景足够；只有 P99（4 秒）来自偶发的连接重建。
- `lib/db.js` 里已有的**瞬时错误最多重试 2 次**（`ECONNRESET` / `PROTOCOL_*` / `malform packet` / `ER_USER_LIMIT_REACHED` 等）是对 Serverless 代理正常抖动的合理防御，**它反而把偶发抖动消化在了用户无感的地方**。

## 3. 线上 500 的完整归因（近 22 天，57 次）

数据来源：`SELECT action, detail FROM sys_op_log WHERE action = 'error.500'`。

| 原因分类 | 次数 | 占比 | 与数据库有关？ |
|---|---|---|---|
| ① **EdgeOne 平台消费了请求体**（`Body is unusable: Body has already been read`） | 37 | **65%** | ❌ 无关 |
| ② **我的 JS 代码 bug**（`Cannot read properties of undefined` 等） | 10 | **18%** | ❌ 无关 |
| ③ **我的 SQL 写错**（`Unknown column 'r.activity_time'` 等） | 7 | **12%** | ❌ 无关 |
| ④ 第三方服务（AI 上游超时 / 邮件） | 2 | 4% | ❌ 无关 |
| ⑤ 其它 | 1 | 2% | ❌ 无关 |
| **⑥ 数据库 / 连接层** | **0** | **0%** | — |

按日分布也印证了这一点：57 次里的 43 次集中在 **2026-09-17～09-21（项目第 1~5 天）**，那是业务代码还在成型的阶段；此后每天 0~1 次。

### 3.1 三类的处理结果

| 原因 | 已做的处理 |
|---|---|
| ① 平台消费请求体 | `readBody` 单独捕获 → **`49406` / HTTP 503**（可自动重试），前端对非 GET 的 5xx 本就重试一次 → 用户无感恢复。另加 `sys_op_log(action='error.bodyUnreadable')` 以便统计真实频率（见 HANDOVER 铁律 #38） |
| ② JS bug | 逐个修复（多数是数组解构写错、`query()` 返回行数组被当成单行等），并补单测锁定 |
| ③ SQL bug | 修正列名并核对真实表结构（`working/schema-dump.mjs`），把"先 dump 表结构再写 SQL"作为习惯 |

## 4. AI 语义层的成功率（另一条独立链路）

数据来源：`ai_usage_log`（每次 AI 调用都落流水）。

| 能力 | 调用次数 | 成功率 | 平均耗时 | 最慢 |
|---|---|---|---|---|
| `chat`（C1 校园问答） | 31 | **96.8%** | 6152 ms | 13837 ms |
| `insight`（C6 问数） | 23 | **100%** | 2283 ms | 5575 ms |
| `action`（C5 对话式执行） | 42 | **88.1%** | 3940 ms | 12023 ms |
| `review`（C2 审核） | 2 | 100% | 2899 ms | 2993 ms |
| **合计** | **98** | **93.9%** | — | — |

`sys_op_log` 里的 AI 失败细分：`chat.timeout` 4 次、`chat.http` 2 次、`upstream.network` 1 次、`chat.network` 1 次 —— **全部是上游网关侧**，没有一次是数据库。

### 4.1 上游抖动的实测特征

密集连打时失败率约 **30~50%**（`working/probe-body.mjs` 连打探针：`/api/ai/action` 6 连打成功 2 次；`/api/ai/chat` 4 连打成功 3 次）。
**这属于上游聚合网关的容量行为，不是我们的 bug，也无法通过换数据库解决。**

应对方式（已在代码里）：
1. **降级优于报错**：上游失败一律返回友好文案（"智能问答暂时不可用，请稍后再试"），业务不受影响；
2. **总预算控制**：`aiJson` 的 `totalBudgetMs` 保证最坏耗时不会顶到平台函数超时（否则平台重试 → 撞上平台消费请求体 → 500）；
3. **一次调用解决一类判断**：C10 相似度用"整体打分"而非两两比对，C5 用一条链路同时支持"执行/问数/问答"，都是在压调用次数。

## 5. 容量评估

### 5.1 数据量级

- 用户 500+，院系 16，班级 14；业务表规模在**千行级**（`sys_user` 最大）。
- 每天的真实写入：请假数条、报修数条、论坛数十条、成绩录入若干批。**没有大表、没有高并发写**。

### 5.2 查询量级

- 每次页面操作 1~3 次简单点查/范围查（`LIMIT 100` 内），无复杂聚合、无多表大 JOIN。
- AI 相关查询额外 1~3 次（知识库召回、权限、流水），仍是小结果集。

### 5.3 结论

TiDB Cloud Serverless 免费额度（5 GiB 行存 + 50M RU/月量级）对本项目是**数量级上的富余**。
**具体的 RU 消耗请在 TiDB Cloud 控制台的 Metrics 页面核对**（本文不臆测具体数字）——
判断依据是：本项目没有大表扫描、没有批量导入（图书导入单次上限 500 行）、没有高频轮询
（未读数轮询为 60 秒一次的单条 `COUNT`）。

若将来要压测或做论文数据，可用 `scripts/e2e-smoke.mjs` 串行跑数轮，同时观察控制台 RU 曲线。

## 6. 如果确实要提升，应该做什么（按性价比排序）

1. **减少冷启动建连**（收益最大）：保持 `connectionLimit: 5` + `enableKeepAlive`（已做）；进一步可把"一次请求内的多次查询"合并（当前若干 handler 有 2~3 次串行查询，可合并不必要的一定要保留的语义检查）。
2. **减少 AI 调用次数**（收益次之）：已通过"一次调用解决一类判断"大幅压缩；后续可在控制台里给不同能力设置更保守的超时，避免长尾拖慢。
3. **升级数据库规格**：只有在"出现真实的连接数上限压力或 RU 限流"时才需要，**当前数据不支持这么做**。
4. **加缓存**：`ai-config` 已有 30 秒模块级缓存、知识库有模块级缓存；若将来首页数据变重，再考虑加一层。

> 一句话：**当前系统没有数据库瓶颈。把精力放在"减少请求往返"和"AI 调用次数"上，收益远大于换数据库。**

## 7. 首屏加载：白屏的成因与修复（2026-10-12）

> 本节把「首屏要等一会、先是白屏」这个**观感问题**量化，并记录修复后的实测值。
> 与 §2~§6 无关：那里的瓶颈是数据库与 AI 上游，这里纯粹是**前端启动时序 + 边缘 RTT**。

### 7.1 结论先说

| 问题 | 结论 |
|---|---|
| 白屏是网络/数据库慢造成的吗？ | **不是。** 本机链路正常（对照组 baidu TTFB 0.109s），静态资源全部命中边缘缓存（`EO-Cache-Status: Cache Hit`），Brotli 已开 |
| 那白屏是什么？ | **`index.html` 的 `#app` 在 Vue 挂载前是空的**，而挂载又被「会话恢复」阻塞 —— 等待期屏幕上没有任何 DOM，即整页纯白 |
| 修复后还白屏吗？ | **基本消除，但不是零。** 启动页在 ~1.0~1.6s 绘制出来并覆盖整个等待期。**剩余的空白只有"文档到达前"那 0.9~1.4s**（边缘 RTT 决定，前端无法消除 —— 文档还没到，浏览器没有任何东西可画） |
| 顺带快了没有？ | **快了。** 已登录用户的会话恢复由 **2 次串行往返降为 1 次**（按单次往返实测中位 0.90s 计，省 ~0.9s） |

### 7.2 白屏的精确机制（代码级）

`src/main.js`（修复前）：

```js
auth.restoreSession().catch(() => {}).finally(() => app.mount('#app'));
```

- 挂载被 `restoreSession()` **硬阻塞**；
- `restoreSession()`（`stores/auth.js`）内部是 `tryRefresh()` → `fetchMe()` **两次串行**网络往返；
- 期间 `index.html` 里只有 `<div id="app"></div>`，**没有任何占位/骨架** → 屏幕上是纯白。

补充事实：首页 `/` 与登录页 `/login` 都**不需要鉴权**（守卫立即放行），但修复前 main.js 对**所有**页面都做同样的阻塞 —— 于是"只是打开首页"也要白等两次登录态往返。

### 7.3 修复（四处）

| # | 改动 | 作用 |
|---|---|---|
| 1 | `index.html` 的 `#app` 内静态内嵌启动页（校徽 + 校名 + 转圈，内联 CSS） | 随文档到达即绘制、不额外发请求；Vue `app.mount()` 会自动清空它；JS 整体加载失败时它留在屏幕上兜底（比白屏可读） |
| 2 | `src/main.js` 门控改为 `Promise.all([restoreSession, router.isReady])` | ① 启动页覆盖整个等待期 ② 首帧渲染时懒加载 chunk 已就绪。**两个都要等**：只等 `isReady` 会带着空 `auth.user` 挂载，`HomeView`/`PortalShell` 会先渲染游客态再跳成登录态（肉眼可见的闪烁） |
| 3 | 新增 `node-functions/lib/user-profile.js`，`/auth/me`、`/auth/login`、`/auth/login-code`、`/auth/refresh` 共用 | 会话用户字段的**单一来源**；`refresh` 现在一次往返即返回完整档案（含 `deptName`/`avatarUrl` 等），杜绝四处各写一份映射造成的漂移 |
| 4 | `stores/auth.js` 去掉 `restoreSession` / `login` / `loginByCode` 三处冗余 `fetchMe` | 每次会话恢复与每次登录各少一次串行往返 |

### 7.4 实测（真实浏览器 · 系统 Edge / playwright-core）

脚本 `.shots/verify-boot.mjs`。三项判定同时给出：**是否真的渲染出来**（防"永远卡在启动页"—— 这是 e2e 抓不到的失败模式：HTML 里确实有启动页，API 也全通，只有真渲染才看得出来）、**启动页是否出现并消失**、**揭开首帧是否为登录态**。

| 场景 | 启动页 出现 → 消失 | 应用渲染完成（墙钟） | FCP | `/api/auth/*` 请求 |
|---|---|---|---|---|
| ① 未登录访客 `/` | 997ms → 2369ms | 2417ms | 1672ms | 无 |
| ② 已登录刷新 `/` | 1602ms → 3306ms | 3302ms | 2076ms | `refresh` ×1（**`/auth/me` ×0**） |
| ③ 已登录直进受保护深链 `/workbench` | 3978ms → 7856ms | 7865ms | 5672ms | `refresh` ×1（**`/auth/me` ×0**） |
| ④ 禁用 JS（模拟 JS 未就绪那一刻） | 常驻 | — | — | 启动页留在屏幕上兜底（截图 `.shots/boot-splash.png`） |

**同一脚本紧接着复测一次（边缘缓存已热）**：① 588ms → 1827ms ｜ ② 521ms → 1674ms ｜ ③ 729ms → 2342ms（`/api/auth/me` 仍为 0、揭开首帧仍是 `梁薇`）。
**冷/热缓存差距很大（③ 7865ms → 2342ms）** —— 这既解释了"刚部署完那一下特别慢"，也说明上表 ① 同样含冷缓存成分。**引用本表数字时必须同时说明缓存状态。**

- ② 的「揭开首帧页头即为 `梁薇`」证明**没有游客态闪烁**；
- ③ 明显更慢，原因是**刚部署完的边缘缓存冷启动**：本次提交使全部资源 hash 变化，③ 是冷缓存下的首次加载 —— 这是"每次部署后第一位访客"的固有代价，启动页同样把它盖住了。
- 另注：EdgeOne 侧会自己跑 `npm install && npm run build`，**其产物 hash 与本地构建不同**（同一份源码可产出不同 hash）—— 验证线上特征时请以线上 HTML 实际引用的文件名为准，不要拿本地 `dist/` 的 hash 去线上找。

单次「Node Function + TiDB 往返」实测（`/api/health` ×5）：**0.64 / 0.66 / 0.90 / 1.32 / 1.36 s**，中位 ~0.90s —— 这就是"少一次串行往返"省下的量级。

### 7.5 已排除的因素（别再往这些方向查）

1. **本机链路**：对照组 baidu TTFB 0.109s / qq TLS 0.406s，正常；
2. **边缘缓存未命中**：静态资源 `EO-Cache-Status: Cache Hit`、`Age: 6~56`；
3. **压缩未开**：Brotli 已生效。

### 7.6 仍可继续做的（未实施，按性价比排序）

1. **`ep-icons` 移出首屏关键路径**：该 chunk 170.95KB（gzip 44.24KB）被 `modulepreload` 预加载 —— 因为 `main.js` 静态 import 整个 `@element-plus/icons-vue`，而 `:is="m.icon"` 用的是字符串组件名、按需插件解析不了。改成"图标名 → 组件"映射表后可动态引入；
2. **背景图 277KB 仍在首屏预加载**（`fetchpriority=high`）与 JS 争带宽，而启动页期间其实用不到它；
3. **把首屏 HTML 交给边缘函数直出**：唯一能消掉 7.1 里那 0.9~1.4s「文档到达前空白」的办法。
