# AI 能力层全系统体检报告（2026-10-10）

> 触发：用户要求"检查系统的方方面面，特别是新加入的 AI 系统，检查和测试，发现问题直接修复"。
> 范围：`node-functions/lib/ai*.js`（22 个）+ `node-functions/api/ai/*`（14 个）+ 与其耦合的服务层与公共模块（`services/*`、`alert.js`、`sse.js`、`http.js`、`guard.js`）。
> 结论：**修掉 3 类 P0/P1 缺陷（越权 / 静默错误 / 总开关失效）+ 1 类并发窗口（频控 TOCTOU）+ 4 项一致性问题**，全部有实测证据与回归测试。

---

## 1. 方法（比结论更重要）

**脚本只用来"定位可疑点"，结论一律以读代码或实测为准。**

一开始用 shell/python 批量扫"每个 handler 是否 try/catch""是否检查开关""logAiUsage 的 kind"等。脚本立刻给出了几个疑点 —— 但**脚本的输出不能直接当结论**：

- 扫 `kind:` 时把**响应体里的 `kind` 字段**也抓进来了（正则跨越了上下文）；
- 扫"是否检查 `ai.enabled`"时，脚本只看 handler，而开关检查在 lib 里 → 差点得出反向结论。

**规范：脚本产出的每一条疑点，都要打开文件读到那几行、或跑一次实测，才能写进报告。** 本报告里每条"后果"都有对应的可复现命令。

### 1.1 四个层次的验证手段

| 层次 | 手段 | 覆盖 |
|---|---|---|
| 静态 | `npm run lint` + `npm run check:import` | 语法、未使用变量、导出是否存在 |

本地直连真实库这一层是本轮的关键：AI 上游当时不可用（见 §4），
但**越权与 SQL 正确性完全不依赖模型**，所以照样能查、能验。

## 3. 发现与修复

### 3.1 P0 · 越权：数据范围判断漏了 `self` 分支

**位置**：`api/af/leave.js`、`lib/services/leave.js`、`lib/services/users.js`（2 处）、`lib/ai-approval.js`

**根因**：`lib/guard.js` 的 `dataScope(roles, deptId)` 返回 `{type: 'all' | 'dept' | 'self'}`；
它在**角色不在 admin/leader/counselor 里**、或**辅导员 `deptId` 为空**时返回 `self`。
而上述几处的写法都是：

```js
if (scope.type === 'dept') { where.push('l.dept_id = ?'); params.push(scope.deptId); }
// ← 没有 else 分支：self 落到"不加任何条件" = 全校可见
```

**实测**（`working/audit-scope.mjs`，直连生产库）：

| 角色 | 请假单可见 | 账号总数 | 应为 |
|---|---|---|---|
| student01 | 1 ✅ | 1 ✅ | 仅本人 |
| **teacher01** | **100 ❌** | **490 ❌** | 仅本人 |
| counselor01 | 23 ✅ | 101 ✅ | 本院 |
| admin | 100 ✅ | 490 ✅ | 全校 |

`api/af/leave.js` 的 `onRequestGet` 更直接：**连角色门槛都没有**，而文件头注释写着
"学生=本人 / counselor·admin·leader=本院或全校" —— **注释与实现不符**，
读代码的人会以为已经拦住了（这比"没有注释"更危险）。

**修法**：
1. `api/af/leave.js` → `actorFrom(context, ['student','counselor','admin','leader'])`
2. `services/leave.js` / `services/users.js` / `ai-approval.js` → 补 `else` 分支，
   **退化为"仅本人"，绝不退化为"不加限制"**

**修复后实测**：教师 请假 **0 条** / 账号 **1 个**；辅导员 101 / 23；管理员 490 / 100。

→ 已升格为 **HANDOVER 铁律 #46**（并补充了"同一天在 4 处旧代码又发现同一个坑"的推论：
凡 `dataScope()` 的返回值必须**穷举三种类型**，改一处时顺手 grep 全项目）。

### 3.2 P1 · 静默错误：把"没算出来"当成"没问题"或给出相反结论

这类缺陷的共同特征：**不抛异常、不崩溃、日志干净**，只给出一个看起来正常但错误的结论。
用户会照着它做判断 —— 危害大于显式失败。

| # | 位置 | 现象 | 后果 |
|---|---|---|---|
| 1 | `lib/ai-triage.js` | AI 降级（没拿到结果）时 `formatTriage` 仍拼出 `[普通] → 后勤处` | **像真实分诊的文本被写进工单备注**，后勤按错误部门派单 |
| 2 | `lib/ai-eval.js` | `judgeReview` / `judgeTriage` 把"能力未开启/调用失败"记成 `ok:false` | 混进**准确率分母与误报率分子** —— 把上游抖动算成"模型判断错"，评估指标失真 |
| 3 | `lib/ai-anomaly.js` | `MIN(due_at)` 取出的是 mysql2 的 `Date` 对象，`String(d).slice(0,10)` | 得到 `Thu Oct 01` 这种「星期 月 日」，邮件里日期不可读（铁律 #40 的老场景，此前只改了展示层） |
| 4 | `lib/ai-summary.js` | "内容太短不需要摘要"与"AI 调用失败"**都返回 `null`** | 调用方无法区分，补摘要按钮一律提示"AI 不可用"（把用户引向错误的排查方向） |

**修法**：
1. 降级时明确输出"未分诊"标记，**不冒充结论**；
2. 新增 `skipped` 状态，**从准确率分母与误报率分子中剔除**；
3. 日期一律在 SQL 侧 `DATE_FORMAT` 取字符串；
4. 导出 `SUMMARY_MIN_CHARS`，让调用方能区分两种情况并给出准确提示。

→ 已升格为 **HANDOVER 铁律 #48**（含"写降级分支时必须自问的三个问题"）。

### 3.3 P1 · 安全与一致性（4 项）

| # | 位置 | 现象 | 后果 |
|---|---|---|---|
| 1 | `lib/alert.js` | 告警邮件 HTML **未转义**直接拼接 | 用户发帖内容可注入管理员邮箱（`<img src=x onerror=...>`） |
| 2 | `lib/ai-review.js` | 确认违规删除回复时**未回退** `forum_thread.reply_count` | 帖子回复数长期虚高（已改为幂等回退，避免重复点扣成负数） |
| 3 | `lib/sse.js` | 上游流**中断**时 `TransformStream` 的 `flush` 不触发 | `pipeUpstreamWithTap` 的 `done` Promise **永不 resolve**，调用方若 `await` 就永久挂起 |
| 4 | `api/ai/review.js` | 用 `49431`（记录不存在）表达"不支持的操作" | 排查方向跑偏（去查记录，而问题在入参）→ 改 `49401` |

### 3.4 P1 · AI 总开关形同虚设

**发现**：全项目 9 个会调 AI 的模块里，**只有 `ai-study.js` 检查了 `ai.enabled`**。

**后果**：管理员在控制台关掉"AI 总开关"后，论坛审核 / 公告摘要 / 报修分诊 /
失物匹配 / 审批助手 / 图书检索**仍然照调不误** —— 与"总开关"这三个字的承诺不符，且在继续烧额度。

**修法**：在**全项目唯一 AI 调用出口** `lib/ai.js` 的两个入口（`aiUpstream` / `aiChat`）
加统一守卫 `aiAllowed()`。**一处生效、全覆盖**，以后新增能力自动受控 ——
逐个模块加必然漏，实测已经漏了 8 个。

**配套细节**：关闭时**不落 `ai.error` 日志**。那不是"失败"而是管理员主动关闭；
若记成错误，关闭期间会持续写日志，还可能凑满"10 分钟 5 次"的阈值
**给管理员发一封"AI 失败"告警邮件** —— 管理员关个开关却收到告警，是典型的自扰。

→ 已升格为 **HANDOVER 铁律 #49**。

### 3.5 P1 · 频控的 check-then-act 窗口（TOCTOU）

**现象**：`consumeAiQuota` 的计数读 `ai_usage_log`，而那一行是在 AI 调用**结束后**才写入的。
「读计数 → 调 AI → 写流水」之间存在**与调用时长等长**的窗口 ——
同一秒内并发的 N 个请求会全部读到旧计数而同时放行。

**修法**：放行时在**本实例**登记一条"在途"标记并计入配额，调用结束后 `releaseAiQuota()` 释放。

**两个关键设计**：
- **标记必须带 TTL 自动失效**：内存计数器最危险的失败模式是"某条路径忘了释放 →
  用户被**永久锁死**"。有 TTL，最坏只是多限制一会儿。
- **诚实标注局限**：EdgeOne 是多实例的，内存 Map 只覆盖当前实例，跨实例并发仍可能略超限额。
  "每分钟 N 次"是**成本控制**而非安全边界 —— **不要把这种补丁说成"已彻底解决"**。

与铁律 #23 的关系：#23 否定的是"用内存计数**当限流本身**"，这里只是给 DB 计数打窗口补丁，两层并存。

→ 已升格为 **HANDOVER 铁律 #50**。

## 4. 与本次体检无关但阻塞 AI 的问题：上游账号欠费

线上最终验收时全部返回 `49430`。翻 `sys_op_log` 找到上游原始报文：

```
400 {"error":{"message":"Access denied, please make sure your account is in good standing.
     For details, see: .../error-code#overdue-payment","type":"Arrearage","code":"Arrearage"}}
```

**即阿里云百炼账号欠费/状态异常。** 此前多轮把这类失败归为"上游网关抖动" ——
**那个判断是错的**，它不是抖动，是账单问题。

**由此新增**（`lib/ai.js` 的 `classifyUpstreamError(status, body)`）：
把上游错误分成 `arrearage` / `rate_limit` / `auth` / `model_missing` / `timeout` / `unknown`，
落库为 `upstream.http.<kind>`，远程一眼可辨；**`unknown` 一律不臆测原因**
（单测里有一条专门锁住"未识别的问题不能被说成欠费"）。详见 `docs/API.md` §5.17。

**教训**：`49430` 这种"统一降级码"必须有**可诊断的下钻**。
"降级设计兜住了用户"不等于"问题已解决" —— 被兜住的问题要查清根因，不能因为不影响功能就放过。

## 6. 已知局限（明确不修，写清楚原因）

| 项 | 说明 |
|---|---|
| 频控跨实例并发 | EdgeOne 多实例内存不共享（铁律 #23）。在途标记只覆盖当前实例，跨实例仍可能略超限额。"每分钟 N 次"是成本控制而非安全边界。 |

| C13 未纳入效果评估 | 评估场景为 `qa / triage / review / insight`（42 条标注用例）。C13 的结果集是**动态 SQL 结果**，判定期望值需要"期望实体 + 期望指标 + 期望分组"，与现有四类的判定器不同构；在补齐专门的判定器之前**不宣称已评估**（避免虚报覆盖）。 |
| 图片/多模态 | 开发测试期硬约束：只用文本（计费高）。 |
