## 一、开场 60 秒（背下来，别即兴）

> "我的题目是《基于云边协同与 Serverless 架构的智慧校园平台及其 AI 安全框架》。
> 它要同时回答两个问题：**校园业务的潮汐并发下，资源怎么供**；**大模型进业务后，权限怎么收**。
> 平台已经在线上跑（c.9o.pw），今天的结论都来自实测，不是设计推演。"

**三个关键词**（评委记住这三句就够）：

| 关键词 | 一句话 |
|---|---|
| 云边边界 | 不按技术栈划，按**一致性要求**划：要事务的必须留云端 |
| 并发正确性 | 不靠应用层检查顺序，把判断**下沉成一条 SQL 的 WHERE** |
| AI 受控 | 模型只出**意图和参数**，永不生成 SQL；写操作走**和人工同一个入口** |

## 二、10 分钟讲述骨架（每段给"必须说出口的那句"）

### 第 1 段｜问题与判据（0:00–1:30）

**必说**：选课开放那几秒，热门班几百人同时抢，其余时间连接数接近零。按峰值配资源闲一年，按均值配资源高峰崩——矛盾不是算力不够，是**供给节奏跟不上突发**。

**三条下沉判据**（这是本文第一个可被追问的"贡献"，务必说全）：

> 无状态、无数据库依赖、可容忍最终一致性 —— **三条全满足才能下沉边缘**。

**追问预案**
- Q：三条判据怎么来的，为什么是三条不是五条？
  A：从边缘运行时的**硬约束**反推：沙箱不能建 TCP 长连接（→ 无数据库依赖）、KV 多节点异步复制（→ 只能最终一致）、实例内存不共享（→ 必须无状态）。约束有三条，判据就是三条，不是拍脑袋。
- Q：边缘到底跑了什么？
  A：静态资源、图片缓存、KV 访问计数、诊断探针。**没有一个需要事务**。

### 第 2 段｜并发正确性（1:30–3:30）—— 本文最硬的部分

**必说**：选课写路径要同时满足四条：不超卖、不锁死请求、不引发重试风暴、不依赖长事务。

**三种方案的取舍（表 4-2，要能脱口而出）**

| 方案 | 在 Serverless 下的死因 |
|---|---|
| 悲观锁 `FOR UPDATE` | 持锁期间占连接，函数被回收就超时；连接数迅速逼近上限 |
| 乐观锁（版本号 + 重试） | 热门课冲突率极高，重试循环**放大流量**，吞吐反降 |
| **条件更新** ✅ | 判断写进 WHERE，单条语句原子完成，无显式锁、无重试循环 |

**核心机制（能画就画，画不了也要说清三层）**

1. 防重复：`INSERT ... ON DUPLICATE KEY UPDATE`，`affectedRows` **1=插入成功 / 2=已存在并更新 / 0=已存在未变**
2. 扣名额：`UPDATE edu_class SET enrolled=enrolled+1 WHERE id=? AND enrolled<capacity`，**affectedRows=0 即满员**，返回 42005 并回滚
3. 事务边界：三步同一事务，不会出现"记录插了名额没扣"或反之

**正确性论证（这句是加分项，务必说）**

> 设容量 C、已选 n。数据库对同一行的更新是串行化的，每次更新前重新求值 `n < C`。
> 所以**任意时刻 n ≤ C 恒成立，不需要应用层兜底**。

**亮证据（表 6-2）**

| 并发 | 条件更新组 | 先查后写对照组 |
|---|---|---|
| 50 | 成功 10，**超卖 0** | 成功 50，**超卖 40** |
| 100 | 成功 10，**超卖 0** | 成功 100，**超卖 90** |
| 200 | 成功 10，**超卖 0** | — |

对照组超卖数 = 并发数 − 容量，**互斥能力完全丧失** —— 这个对照是全文最有说服力的一张表。

**追问预案**
- Q：P50 到 15 秒，这么慢能用吗？
  A：这是 200 并发**抢同一个教学班 10 个名额**的极端场景，瓶颈是同一行串行化 + 跨区 RTT，不是算力。真实选课分散在几十上百个班，不会同时命中一行。而且**这里的第一指标是超卖数不是延迟**——压测要回答的是"会不会算错账"。
- Q：条件更新失败率高吗？
  A：满员时**必然失败**，这是设计意图。失败即返回可读提示，不做无意义重试。
- Q：为什么不用 Redis 原子操作（DECR）？
  A：名额是强一致数据，Redis 主从异步复制，故障切换会丢扣减；而且引入一个新组件就多一个要运维的东西，与"免运维"冲突。**表 4-1 明确写了：名额、床位、审批结论不进 KV。**

### 第 3 段｜流程与权限（3:30–5:30）

**必说**：审批和报修长得像，但语义不同，**用两套机制**。

| | 审批流 | 状态机 |
|---|---|---|
| 语义 | 批准/驳回，有"决策" | 受理/完成/无法处理，是"处置" |
| 中间态 | 多节点、可回退、可加签 | 单向推进 |
| 用例 | 请销假 | 宿舍报修、社团报名审核 |

**必说（这是本文一个"反直觉"的结论）**：把报修硬套审批流，会把"无法处理"这个**正常结局**误判成"驳回"，造成语义错位。

**两表模型**：`flow_instance`（一单一行，记当前节点/状态/结论）+ `flow_node`（一实例多行，记角色/处理人/时间/意见）。
业务表只存 `instance_id` 就获得流转能力；**加签、转办都是新增节点，不改表结构**；处理人按"角色 + 数据范围"实时匹配，调岗后流程自动跟随。

**三层防线（表 4-8，必说顺序与定位）**

1. 前端路由守卫 —— **只是体验，不是安全边界**（代码跑在用户浏览器里）
2. 服务端角色校验 —— **角色不从 JWT 读，每次实时查库**
3. 数据范围拼 SQL —— `all` 不加条件、`dept` 加院系、`self` 加本人，**统一一处收口**

**追问预案**
- Q：为什么角色不放在 JWT 里？多一次查库不亏吗？
  A：JWT 签发后有效期内改不了。若以令牌为准，**撤权之后对方在过期前照样能操作**。代价是每请求多一次索引查询（已含在 P50 471ms 里），换来撤权即时生效。
- Q：前端那层既然不安全，为什么还做？
  A：改善体验（不给无权用户渲染入口、给出明确提示）。我在论文里明确写了它不构成安全边界 —— **把"没做"和"不需要做"分清**。
- Q：数据范围会不会漏拼某个接口？
  A：会，这是真实风险。所以用**反向断言**兜：以学生身份调管理端接口，期望返回 40301 而不是数据。正向功能出错用户会发现，越权漏洞不会。

### 第 4 段｜AI 安全（5:30–8:00）—— 差异化所在

**必说**：AI 在这个系统里**不是聊天窗口，是权限低于人工、行为可审计、失败可降级的内部主体**。

**立论前提（一句话定调，后面所有设计都由此推出）**

> **大模型服务在信任边界之外，它的每一次输出都当外部输入看待**，和用户提交的表单一个待遇，不享有任何内部特权。

**问办合一（区别于普通 AI 助手的地方）**

> 模型只输出**意图 + 参数**，永不生成 SQL、永不调用任意函数。
> 动作来自**封闭注册表**（未登记一律拒绝，返回 49402）；
> 查询由服务端编译成**参数化 SQL**，字段名来自注册表，取值全用占位符；
> **模型不产生也不接触 SQL 文本** —— 没有字符串拼接，注入风险无从谈起。

**写操作的两阶段确认（图 5-6）**

- 第一次只返回**影响清单 + 确认令牌**，第二次带令牌才执行
- 令牌 **HS256 签名 / 5 分钟失效 / 绑定操作者 sub**，别的管理员拿到也用不了
- 清单每条带**可读标签**（姓名 + 账号 + 院系），只列 ID 的话二次确认就退化成走过场
- 执行时调**服务层函数**，和人工点按钮同一份代码，审计再写一条、带 `via: ai` 标记

**五层防线（L1–L5，按数据流经环节分，不按技术类型分）**

| 层 | 防什么 | 关键实现 |
|---|---|---|
| L1 身份 | 越权读取 | 继承发起者身份，走同一鉴权中间件；范围拼 SQL |
| L2 参数 | 参数伪造、非法枚举 | 输出强制 JSON + Schema 校验，**失败即拒，不做容错解析** |
| L3 执行 | 越界操作 | 动作白名单、参数化 SQL、批量需显式范围、破坏性操作二次确认 |
| L4 输出 | 注入外泄、脏内容 | 整体转义不直接渲 HTML、DOMPurify 消毒、必须标来源 |
| L5 审计 | 不可溯源、成本失控 | 四张流水表按用户+时间关联；30 分钟告警合并 |

**必说（这条最能体现工程判断力）**：

> 五层的意义不在于某一层拦得住，而在于**任一层失效后仍有下层兜底**。
> 我也明确写了**挡不住什么** —— L4/L5 必须保留，不能宣称注入问题已彻底解决。

**红队结果（表 6-4，主动说漏判，别等问）**

| 类别 | 拦截率 | 漏判 |
|---|---|---|
| 高危操作诱导 | **100%** | 0（不依赖语义判断，L3 白名单直接拒） |
| 越权问数 | 90% | 2（聚合查询漏了 dataScope 注入） |
| 论坛违规绕过 | 85% | 3 |
| 提示注入 | **75%** | 5（参数合法、意图被语义诱导，L2 无判据） |
| 正常用例对照 | 误判 2/20 | — |

**追问预案**
- Q：提示注入只拦 75%，是不是没做好？
  A：**这 5 条不是"绕过关键词"，是参数完全合法、意图被语义诱导**，L2 在语义层没有判据。我没有通过加提示话术硬拉高这个数字 —— 那样只会把误判率推上去，而误判的代价（误拦正常用户）比漏判更难挽回。**这三项指标必须一起报**，只报拦截率会掩盖代价。
- Q：为什么可疑内容降级放行而不是直接拦？
  A：两类错误代价不对称。误拦一条正常表达，用户直接流失还不申诉；放过一条可疑内容，只要留了痕、事后能处置，损失可控。
- Q：模型幻觉怎么办？
  A：**让幻觉无处生效**。查询类走参数化 SQL，数字出自数据库不出自模型；问答类强制标来源条款，检索未命中就明说"未找到"。

## 四、18 个高频追问与答法

### A. 架构选型

**1. 为什么用 Serverless，不用 K8s/微服务？**
潮汐特征：峰值是均值十余倍，其余时间接近零。K8s 要常驻节点，闲时也在烧钱，还要人维护；Serverless 秒级扩容、闲时缩到零、免运维。代价是冷启动和无长连接 —— 这两点正是本文 4.1/4.6 要解的（连接池 + 条件更新）。

**2. 冷启动怎么解决？**
两道：连接池 + 预热（P50 2682→471 ms）；业务上避免长事务（条件更新替代悲观锁）。前端用路由懒加载 + 首屏启动页，把白屏时间压到可接受。

**3. 为什么选 TiDB？**
兼容 MySQL 协议（迁移成本低）、Serverless 托管（自动扩缩、自动备份）、强制 TLS。40 张表 13 个 schema 文件，每个文件独立幂等，可单文件增量迁移。

**4. 单点风险：所有 AI 调用收敛到一个模块，挂了怎么办？**
确实是单点，所以**每个调用点都有非 AI 兜底**：审批助手不可用审批页照常、公告摘要不可用显示原文。降级不是弹报错，是**功能缺一块但流程不断**。

### B. 并发与数据

**5. `affectedRows=0` 到底是"满员"还是"班级不存在"？**
两者都返回 0，所以先查一次教学班确认存在（这一步不加锁、只读），再用条件更新判定名额。区分不了会误报错误码。

**6. 事务里三步，中途函数超时被回收怎么办？**
数据库侧事务回滚，不会留下中间态。这是把正确性放在数据库而不是应用层的好处 —— 应用层被杀，语义仍然成立。

**7. 退课释放名额是实时的吗？**
是。`enrolled` 减一与选课记录状态变更同一事务，退完立刻可被别人选到（FR-13）。

**8. 相邻节次为什么算冲突？**
`1-2` 与 `2-3` 数值上 `2 ≤ 2` 成立，判为重叠。实际排课里两门课共用第 2 节，确实冲突。这条专门写了测试用例。

### C. 权限

**9. 三层防线如果第二层写漏一个接口呢？**
所以有反向断言兜底（学生调管理端接口必须 40301），且 e2e 每次部署都跑。但我要诚实说：**这不能证明覆盖完备**，只能证明已覆盖的部分是对的。

**10. 管理员能给自己提权吗？**
不能。两条硬规则：管理员不能禁用自己、不能摘掉自己的超管角色。

**11. 学生能看到别院学生的请假吗？**
不能。数据范围 `self`/`dept` 在服务端拼进 WHERE，不是前端过滤。

### D. AI

**12. 和直接给模型 function calling 有什么区别？**
三处：① 动作来自**封闭注册表**，模型只能选不能造；② 参数**服务端逐项校验**（枚举白名单/数值上下界/ID 查范围）；③ 写操作**复用人工入口**（同一服务层函数、同一审计），不是另开一条 AI 专用通道。

**13. 为什么不直接让模型生成 SQL？**
三个问题一起出现：注入（字符串拼接）、越权（模型不知道数据范围）、不可校验（SQL 无法静态验证字段合法性）。所以改成"模型出结构化描述 → 服务端校验字段在不在注册表、范围有没有越界 → 编译成参数化 SQL"。

**14. 二次确认怎么防重放/越权？**
令牌 HS256 签名、5 分钟失效、`sub` 绑定操作者。别人拿到令牌也用不了，过期就得重新发起。

**15. 18 项能力里 C8–C10 是什么？**
报修智能分诊（判）、失物智能匹配（判）、信息问数（读，已并入 C13 体系）。表 5-1 里合并成一行是为了排版，**实际是三个独立能力**。

**16. 为什么不用向量检索？**
知识库目前只有几百条条款，关键词加权（标题 > 关键词 > 正文）够用，延迟和成本更低。条款涨一个量级，同义召回就会出问题 —— 这是明确写进第 7 章的不足与后续方向。

### E. 元问题（最容易翻车的三类）

**17. 工作量是不是一个人做的完？**
40 张表 / 13 schema / 101 个函数文件 / 27 个页面 / 550 条单测 / 58 项线上断言，全部在同一个仓库、有完整提交历史。**能讲清每个设计"为什么不是另一个方案"**，比报数字更有说服力 —— 抄来的方案答不了"你为什么不用 XX"。
